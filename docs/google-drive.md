# Google Drive

Part of the Explorer Native notes for Claude; CLAUDE.md says when to read this file.

## Google Drive (a WinFsp volume, 4.3.0)

A real file system on WinFsp (winfsp.dev): `WinFsp.cs` binds the DLL for the process's processor (winfsp-a64/x64.dll from the 32-bit registry's InstallDir), and `DriveMount` answers Windows (`DriveMount.Volume.cs`). It is a network-type volume (WinFsp.Net, UNC `\\GoogleDrive\<account>`, `GoogleDrive.VolumeName`), so Windows makes no Recycle Bin or index on it; Explorer's label comes from `MountPoints2\##GoogleDrive#<share>\_LabelFromReg` (`LabelTheDrive`). The volume's security descriptor is the signed-in user and SYSTEM only (`WinFsp.UserOnlySecurity`): the UNC name is visible to every session. Scope is full `drive`, so bugs can damage the account. Off by default. 4.2 and earlier were a Cloud Files sync root on a subst letter, where other programs' writes never reached Drive (Morgan, 4.2.10: a 204 GB folder moved in PowerShell vanished from F:); `LegacyCloudFiles.Sweep` (every start, `SweepOrphans`) unregisters and deletes those folders and letters.

- Never walk the letter from the app: panes use the mount's listing (`TryListing`), and walking costs a Drive listing per folder. F5 forgets that listing first. Listing names are the names on the letter after `Sanitise`/`Unique` (`DrivePlaced`). The volume answers from `_listings` (`RowIn`, indexed per listing array by a ConditionalWeakTable); a listing older than `FreshFor` (30s) is served and re-listed behind (`RefreshBehind`); a name not found is listed again at most every `MissRelistAfter` (30s) per folder, so a file made on the web opens by path. `CommitListing` diffs old and new (`NoteListingChanges`): Windows is told (`Changed`, a background notifier calling `FspFileSystemNotify` in batches, names normalized via `DisplayPath`) and a file whose size or date changed loses its cache.
- Requests cost ~700ms each. Reads are served from `DriveFileCache` (4MB chunks, 1GB pool) by `ReadFromDrive`, a piece (`PieceBytes`, 256KB, at most to a chunk edge) at a time with `DataDeadline` (90s) per piece, never answered short (a short read looks like the end of the file). Cold reads wait 400ms, then fetch at most 1MB themselves. `MaxOpenFiles` is 3. `SweepIdle` never runs during requests (`_callbacksInFlight`, the `InFlight` guard). Caches are leased.
- A cache does not download in its constructor: it starts when warmed (leased and let go unread) or after ~1MB of straight reads, so a tag or thumbnail read costs one small range. Read-ahead is a sliding window of 4, bounded past the furthest chunk read, retrying a failed chunk.
- Folder sizes on the letter come from `DriveSizeIndex` (DriveFolderSizes.cs): one listing of the account, split by modifiedTime slices 8 at a time, then the changes feed every 20s. One index per drive. Never size a Drive folder by walking it. Once `Built`, `FolderSizeAsync` waits at most `AnswerWithin` (2s) for the feed and answers from what is held (4.2.1, Conner: sizes missing half the time, because each folder waited out the feed and navigation cancelled it). My Drive's index starts at connect when sizes are Automatic (`WarmSizes`). The Shared drives folder is the sum of every shared drive's index (`SharedDrivesTotalAsync`), null until all are known.
- 4.2.4: each index is saved between runs, DPAPI through `ProtectedFile.WriteAllBytes`, at `%APPDATA%\ExplorerNative\DriveSizes\<sha256(account)[:16]>-<driveId|mydrive>.bin` (compact: ids once, parents as indexes, Brotli). The first refresh loads it and asks the changes feed from the saved bookmark; 400/404/410 still falls to `RebuildAsync`. Saved after every whole listing, after feed changes at most every `SaveEvery` (10 min), and at unmount (`SaveNow` in TearDown). `ForgetSignIn` deletes the folder, `MaySave` (HasSavedSignIn) stops a late write after sign-out, and another account's files go at the first size question. Log lines start "sizes:" in EXPLORERNATIVE_DRIVELOG.
- 4.2.4: listings (files.list, changes, drives.list; `DriveClient.IsListing`) ask for gzip per request (Accept-Encoding plus a User-Agent containing gzip), and `Send` unpacks them (`Unpacked`). The shared handler is not set to decompress, so ranged reads (alt=media) and uploads stay untouched. `EXPLORERNATIVE_SELFTEST_ONLY=sizebench` with `EXPLORERNATIVE_BENCH_DRIVE=<name>` times a real whole listing with gzip off and on (API only, never the letter).
- `Populate(..., interactive)`: interactive (callbacks, navigation, search, web app) uses the 15s client, 2 tries, no outage wait; patient (uploads, CreateFolderIn, NamesIn, IdOrRelist, ChildrenOnDrive, PopulateRoot) waits blips out. A patient caller made interactive can create duplicate folders on a blip. CreateFolderIn refuses when the parent has no listing.
- Offline with a cached listing answers from it, without marking the folder fully populated; back online, those folders are listed again.
- Writes (DriveMount.Writes.cs, DriveStreams.cs): nothing on the PC's disk (Conner: "uploading should not use the PC's space but other apps should still be able to write to it"). A file being written is a `Pending`: its base on Drive (`HasBase`, `BaseSize`, read through the chunk cache at `DriveSize`, sizes taken from the mount at `Hold` time, never the handle's) plus what was written since, by offset, in memory (`ByteOverlay`, counted by `Allocated` buffer bytes, runs joined when they touch). Two locks per file: `Gate` for state, never held across the network; `Send` (a semaphore) for one upload at a time, held across it. Lock order: hold gate, `_treeGate`, `Gate`. A new file up to `MemoryFileBytes` (4 MiB) goes up in one request (`UploadFromMemory`) `Settle` (3s) after its last handle closes (`Detach`), so scratch files never reach Google; a file left open with nothing written for `IdleCommit` (30s) goes up too (Office keeps documents open). A bigger new file streams while written: `StreamSome` (from the write, at most `PiecesPerWrite` pieces within `PieceDeadline`, never waiting on another upload) sends whole `ChunkBytes` (8 MiB) pieces from `Sent` through a session opened with no length (`BeginStream`, `SendPiece`: "bytes a-b/*", the last "bytes a-b/total"), always keeping the last byte back (or adding a zero byte the next pass cuts). Writes below `FrozenBelow` (under a piece being or already sent) go to `Late` and are the next pass, which re-reads the rest from Drive; a memory commit freezes everything. A new file lets each sent piece go (`LetGo`); an edit of a Drive file keeps its bytes and does not stream unless memory is short (`Pressed`). A cut below `FrozenBelow` settles first (`SetLengthPending`): nothing let go, or a cut to zero, drops the session (`DropSession`, aborting the upload in flight); otherwise the session is finished, then cut. Never cancel a request that may make the file (`MayFinish`: a small file's one request, or a last piece naming the total): Google can finish it with the answer lost, and forgetting it left a duplicate or a deleted file back on Drive (4.3.0 re-review). A last piece already sent is settled with Google (`AskHeld` with `FinalTotal`) before anything is dropped. A delete of a new file marks it under `Gate` with its id read (`MarkDeleted`); `Landed` reads `Deleted` the same way and trashes what an upload made meanwhile. An existing file is marked only once Google trashed it, so a refused delete keeps its edits. A small new file's create keeps its tag across tries (`CreateTag`, `CreateParent`, `CreateTried`, `UploadFromMemory(tag:)`): a later try looks it up (`MadeWithTag`) and replaces it; a deleted one whose create went unanswered is looked up and trashed (`TrashLostCreate`). After a refusal writes fail with `RefusedStatus`. A piece that fails leaves `Unsure`: before more is sent `AskHeld` asks Google how much it kept (Google ignores bytes it already has, so writes there must be Late); once the last piece was named, `FinalTotal` fixes the total. A session Google ended starts over only when nothing was let go. A read of bytes let go finishes the upload first. `Landed` makes the answer the base under `_treeGate`; a new file renamed or moved while it went up is moved on Drive after (and `RenameOpened` moves one that landed just before its re-key), and a date set meanwhile is a metadata PATCH. `TryAttach` refuses a pending being let go (`Retired`), and `Hold` looks again. A write in progress counts in `Writing` (and stamps `LastWrite` when it ends, its own pieces included): such a file, or an open one with a session, is never taken for idle by the idle commit, the squeeze or the quit drain, and an open file is committed in one pass. Memory: past `HoldMost` (512 MiB) across files a writer whose file holds little waits (`WaitForRoom`, 2 min) while closed and briefly idle files are sent (`_squeezedUntil`); a file over `FileMost` (128 MiB), or any while memory is short, sends what it has with gaps as zeros, patched later; late patches over a few MiB finish the upload under pressure (`LateTooBig`). Offline nothing streams and a write that would hold more than `FileMost` fails at once. A file over `FileMost` whose session another upload holds waits for it (`StreamSome(wait:)`, `PieceDeadline`), and over twice that the write fails (DiskFull), so memory stays bounded. Every callback's waits together stay under `CallbackMost` (4 min), below WinFsp's 5 min IrpTimeout. Quit: `ChooseWhatDrains` (before the unmount) picks every dirty file not written in the last 2s, `DrainUploads` sends them for `DrainFor` (60s), and whatever is left is said by name (drive.save.failed); handles closed while stopping are not saves (`_stopping`). The tray's Quit asks first while `UploadNames` is not empty (`ConfirmUnsavedDrive`). Google refusing for good sets a file whose bytes can still be put together (nothing let go) aside in `UnsavedFolder` and says so (`Refuse`); anything else retries 5s doubling to 5 min. The fake Drive enforces 256 KiB pieces and unknown totals like Google, ignores re-sent bytes below what it holds, refuses a total below it, and rounds a broken streamed piece down to 256 KiB. Tests for each review finding: `HardeningTests` in DriveMountTests. Measured live: 60 MB written with C: free space moving under 30 MB.
- Folders, renames, moves and deletes are one request each, while the program waits (`Create` with FILE_DIRECTORY_FILE, `RenameOpened`, `DeleteOpened`). Rename sends name and parents in one PATCH and then `MoveKey` re-keys maps, listings, held copies and open handles (`RekeyOpened`; WinFsp forbids renaming a folder with open files under it). Replacing trashes the replaced file (`ReplaceAway`). Deletes go to the Drive trash; a trash Google refuses leaves the entry for the next listing and is said. Read-only: the Shared drives list and anything under Trash (`ReadOnlyAt`); never renamed, moved or deleted: the root, those two, and each shared drive (`Fixed`). A date set alone is a metadata PATCH (`SetModifiedTime`), never a re-upload.
- Offline: `LetterFollows` removes the mount point when `DriveHealth` goes Offline and puts it back (another free letter if it was taken) when Online; open handles keep working. `Letter` stays the assigned letter while hidden so paths still mean Drive; `LetterShown` says whether it is there. `Probe` asks `Whoami` every `Every` (60s), every `WhileOffline` (10s) when hidden, and three times at once on a network change; it also keeps `QuotaUsed`/`QuotaLimit` (the volume's size) current.
- Tests: `EXPLORERNATIVE_SELFTEST_ONLY=winfsp` (bindings over a file system in memory) and `drivevolume` (DriveMountTests mounts the volume on a free letter over FakeDrive and drives it with .NET, cmd, robocopy and PowerShell in their own processes, Word's temp-file save, File.Replace, restarts, refusals, offline). They need WinFsp installed. The fake maps "root" to My Drive on list, create and move; mount the rig at "root" so the root has Shared drives and Trash.
- Never call `GetOrAdd(key, factory)` for caches or folders. Use the value overload or `Lazy`.
- Check layouts against winfsp.h. `WinFsp.CheckLayout` compares sizes (VOLUME_PARAMS 504, FILE_INFO 72, DIR_INFO 104, VOLUME_INFO 88) and `TryLoad` refuses to load on a mismatch. Callbacks are `UnmanagedCallersOnly` trampolines that catch everything; file contexts are GCHandles (UmFileContextIsUserContext2); directory listings go through WinFsp's DirBuffer so marker handling and sorting are its own. FlushAndPurgeOnCleanup and PostCleanupWhenModifiedOnly are set; IrpTimeout is 5 min, so a held download (`HoldHere`) is capped at 9.
- Never answer a short read as success, and never take a 200 as a range.
- Bad connections (4.2.7, Conner: nvda.7z sat at 100 percent then error 389/379). `ReadRange` keeps what arrived and asks only for the rest; it gives up after `ReadQuietBudget` (45s) of silence, not a total time. Callbacks hand Windows at most `PieceBytes` (256KB) at a time, `DataDeadline` (90s) per piece. A read waiting over 8s on a chunk fetches its own bytes and the read-ahead drops to one stream for a minute (`_slowUntil`). Once Windows itself times a read out (426), it refuses that file with 379 until the app restarts, so a copy out of Drive tries robocopy only twice (`RetriesFor`) and then `RoboCopyEngine.DownloadFromCloud` (`GoogleDrive.DownloadOutAsync`) fetches each failed file straight from Google, MD5-checked. Test with `EXPLORERNATIVE_BADNET` (src\BadNet.cs, off unless set): "rate=KB/s,drop=bytes,stall=0..1", or "file:path" to change it while the app runs. `EXPLORERNATIVE_DRIVELOG` logs every data callback. Quick group: `EXPLORERNATIVE_SELFTEST_ONLY=badnet`. Measured: 4.2.6 failed nvda.7z nine times at 400KB/s with drops; 4.2.7 copies it first time.
- Quit order: player and prefetcher, then `WaitForReads`, then `DriveMount.Dispose` (`WaitForCallbacks`), each bounded at 5s.
- Prefer the API to the letter inside the app (it is answered by this same process; reading it from a UI thread waits on our own dispatcher). Use UseShellExecute plus an output file for probes, and `dotnet-stack`.
- Every write branches on `Drive.Owns` (CreateFolderIn, CreateFileIn, RenameOnDrive, delete, paste).
- The file manager's own operations still go through the API (`Drive.Owns`), with `PlaceOne`/`RemoveOne`/`MoveLocal` keeping the letter in step and telling Windows; delete goes to the Drive trash and the entry is removed only after Drive agrees. Verify by restarting.
- Moves are one PATCH. A move out trashes only what `VerifyCopied` shows arrived. Check permissions first. Refuse selections mixing Drive and local items.
- Copy inside Drive is server-side `files.copy`, with folders recreated. Settle the name first. Overwrite means copy under a free name, then trash the old. Never swap file and folder, never copy into itself. A destination that will not list fails rather than duplicating.
- Names are not keys on Drive. Always check conflicts, and "could not list" means ask. Replace means upload, then trash. Folders merge. `PlaceOne` seeds `Unique` from the listing.
- A retried create first looks for its own `appProperties` tag. If it cannot look, it does not resend.
- A rate limit (429, or 403 rateLimitExceeded/userRateLimitExceeded: `IsRateLimit`) never spends an attempt in `SendWithRetry` (not interactive), `UploadWhole` or `UploadResumable`: `SlowDown` waits 2s doubling to 60s (or Retry-After) for up to `RateLimitPatience` (1 hour, counted in waits, not the clock), then the file fails (Conner, 3.0.14: a big paste spent six tries in two minutes and ended in a dialog). The folder monitor opts out (`CallerWaitsOutRateLimits`, set in `Patiently`), because its own wait shows in the pair's status and stops on Pause. Google's 750 GB/day cap arrives as plain `userRateLimitExceeded`: a limit lasting past 3 minutes (`DailyLimitAfter`, counted in waits) is said as `DailyUploadLimitSaid` ("You've reached your daily upload limit for Google", Conner's words), rechecked every `DailyCapRecheck` (15 min) and never given up on; a copy says it once an hour at most (`drive.upload.dailylimit`).
- Uploads stream. On failure, query the session and rewind to Google's count. A 308 with no Range means zero bytes held. Small files get 6 tries (408/429/5xx only, jittered), with stream and request rebuilt each try. Uploads use a stall watchdog, not a timeout. 4 file streams, 8 folder streams. Empty folders are created and links are skipped.
- The file manager's moves, renames and trashing pass `retry: true` (`MoveOrRename`, `Trash`), and `RightsOf`/`NameOf` always retry; the folder monitor's calls keep one try. F2 and the web rename are `interactive`. An interactive request whose quick try timed out gets one longer try (`InteractiveSlowAttempt`, 30s), still cut by the caller's deadline. A folder copy inside Drive notes a file or subfolder Drive refuses through `DriveCopyReport.OnFailed` and carries on (unset, the first failure ends it). Upload windows get a heartbeat report each second; `RecentRate` stretches its window up to a minute when nothing moved inside ten seconds, so Drive's 4MB pieces never read as "unknown". Tests: `EXPLORERNATIVE_SELFTEST_ONLY=drivecopy`.
- `Explain` error bodies (never dump HTML). Cap error lines at 300 characters, cutting from the end.
- Auth: built-in client (100-user cap), with a client JSON file taking precedence. In production, so no weekly expiry. Loopback redirect needs `ContentLength64`. Bump `ScopeVersion` on any scope change. `_tokenGate` serialises refreshes. Consent is per call, never inside a filesystem callback. Only `invalid_grant` deletes the token. Sign-out is local.
- A bare TaskCanceledException is our own cancellation, not "offline".
- WinFsp is not shipped: `WinFspSetup.InstallAsync` downloads WinFsp's own signed MSI from its GitHub release, checks it against the pinned SHA-256, and runs it with runas; the tray asks first (`OfferWinFsp`) when a mount stops on `NeedsWinFsp`; No or a failed install turns Google Drive off, saves it, and says so in a dialog with how to turn it back on (`TurnOffDriveWithoutWinFsp`). WinFsp's licence (native\WinFsp-LICENSE.txt) asks for its credit (`WinFspSetup.Credit`) in the UI (Preferences, Google Drive; the install question) and the docs.
- Trash: a virtual folder like Shared drives (`DriveClient.TrashId` "::trash", `TrashName`), after Shared drives at the account root while `ShowTrash` is on (`Settings.ShowDriveTrash`, default on; `GoogleDrive.SetShowTrash` forgets the root). `ListTrash` keeps only explicitlyTrashed, My Drive only (`corpora=user`). Drive can only list everything trashed, children of trashed folders included (Conner's 64 items: 68s, past the 45s callback deadline), so `ListTrash` answers from a kept copy (4.1.5): `WarmTrash` lists it patiently at mount, `Trash`/`Untrash`/`DeleteForever`/`EmptyTrash` edit the copy (`EditHeldTrash`, also replayed onto a listing in flight), and a copy over `TrashFresh` (5 min) is re-listed behind the answer. Apple Music Autoplay is `Settings.AppleMusicAutoplay` (default on) via `AppleMusic.Autoplay`. Folders under it list with `trashed = true` (`ListChildren(trashed:)`, `DriveMount.IsUnderTrash`). `RestoreFromTrash`, `DeleteForever` and `EmptyTrash` act only on items directly in Trash (`TrashItem`). Every write refuses the trash at any depth (`InTrash`), and so does `Request()` for TrashId. MainForm asks every time, No by default; Delete inside Trash is Delete permanently. `DeleteForever` asks Drive `trashed` right before the DELETE (Drive deletes live files just as readily, and the held copy can be minutes old). Claude never runs the permanent ones against the real account. Tests: `EXPLORERNATIVE_SELFTEST_ONLY=drivetrash`; the fake Drive treats "root" as My Drive and supports DELETE and emptyTrash.
- Shared drives: a virtual folder, `supportsAllDrives=true` on every request, listings carry `driveId`, nothing is created in the virtual list, search covers one drive at a time.
- The search rule is `SearchQuery` (FileSearch.cs, 4.2.0), shared by the local walk and Drive: words in any order, folded with `TypeAhead.Fold`; a word may be in the folders below the searched one but one must be in the name; quotes; * and ? patterns (even quoted); -word excludes by name or folder. Drive asks Google for any one `DriveHints` word, then `DriveSearch.Answering` applies the whole rule with folder names from the graph before any folder is populated. A quiet re-run after an operation in results (`RerunSearchAsync`) is not awaited and lands on the item.
- Search goes through the API with a cached folder graph and `RootId`. Paths come from ids (`PathForChain`). The local walk uses an explicit stack, stops at a cap and says so.
- Copy to clipboard warms the file; cut does not. Copy out uses robocopy `/A-:O /DCOPY:T` with one thread. Progress is the union of ranges served.
- `ForgetGone` drops vanished ids, but never a held file's or one uploaded in the last minute (`UploadedRecently`: Google's listing lags a create).
- `Sanitise` substitutes rather than trims: illegal characters, empty-after-trim, device names (`CON_.flac`), names over 255. Google Docs are skipped.
- Setup failures, 7.1.0 (review: "make the failure messages say which part is wrong"): said through `GoogleSetupErrors` (src\GoogleSetupErrors.cs, pure, group userfixes): invalid_client (wrong ID or wrong secret), deleted/disabled/unauthorized_client, redirect_uri_mismatch (Web application instead of Desktop app), access_denied mentioning verification (not a test user: Google Auth platform, Audience), org_internal, admin_policy_enforced, invalid_grant, Drive API off (accessNotConfigured, SERVICE_DISABLED) and Drive unticked on the permission page (insufficientPermissions). `GoogleSetupException` carries the sentence and is never retried as a network failure. `GoogleDrive.SetupProblem` finds it in an exception chain and wins over "sign-in was not finished". Google's "Access blocked" page never redirects back, so its hint is in drive.signin.timeout. The client check refuses only `RefusesClient` codes; invalid_grant is the right answer to a made-up code. Console menu names were written from memory, not checked live.

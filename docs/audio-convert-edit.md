# Converting and editing audio

Part of the Explorer Native notes for Claude; CLAUDE.md says when to read this file.

## Converting and editing audio

- Context-menu commands (Convert audio, Edit audio), shown by name only. Edit audio is not on the Drive letter; Convert audio is (6.1.0), only not in the Drive trash.
- Converting on Google Drive (6.1.0, Conner: his Recordings, LifeRecorder folder is 112 GB with FLACs up to 20 GB): `AudioConverter.ConvertOnDrive`. Nothing is encoded on the letter (a file written there is held in memory and encoders seek back). Each original is fetched with `GoogleDrive.DownloadOutAsync` into `%TEMP%`, ExplorerNative-Convert, one folder a file (`WorkRoot`), converted there, uploaded beside the original with `UploadInto`, confirmed by `GoogleDrive.WhyNotUploaded` (Google's size and MD5 against the local file), and the work folder deleted. Gather, Plan and Resolve use the mount's listings (`GatherOnDrive`, `GoogleDrive.Known`), never the letter. `WorkBudget` is 1 GiB across the files running at once (Conner: "no more than a gigabyte at a time"): original plus `EstimateOutput`. A file that fits and finds room now (`TryAcquireWork`) is downloaded first; otherwise it goes straight through with nothing on disk (`ConvertStreaming`, two at once, `_streamers`), and a file too big for the budget only ever goes that way (Conner: "if the file is 100 gigs alone it should split the file and handle putting it all back together"). Straight through: the original is read through the letter, and the encoder writes into a `SpoolStream` (src\DriveSpool.cs) that `GoogleDrive.StreamInto` sends in 8 MiB pieces over a session of unknown length (`BeginStream`, `SendPiece`), under a `.converting-` name, a few pieces in memory at most. An encoder that goes back to finish its header after that piece has gone (WAV, MP3, M4A; not Opus or Windows' FLAC) leaves `Late` writes, and a second pass reads Google's copy back a piece at a time, puts them in and sends it as the same file's new contents. Size and MD5 are checked against Google's, then the file is renamed to its real name; any failure trashes the temporary file. Every encoder takes an optional output stream (`AudioEncoders.Create(output:)`; Media Foundation through `WritableIStream` and `MFCreateMFByteStreamOnStream`). Tags that Windows writes afterwards (MP3, M4A, WAV) are not written on a file sent this way. Under 16 MiB of output nothing has gone before the header is finished, so a live test of the second pass needs a bigger file. `DriveTries` (3) for trouble that is Drive's (`ConvertRetryException`), never for a file that will not decode; before an upload is sent again the folder is listed for the first one. Tests: group convert; real folders with `EXPLORERNATIVE_SELFTEST_ONLY=convertprobe` and `EXPLORERNATIVE_CONVERTPROBE_DIR`.
- Delete original files (6.1.0): a box in the dialog, never remembered, off each time. `RemoveOriginal` runs only after the file's conversion returned and never once cancelled; Recycle Bin (`ShellDelete.RecycleWithoutUi`) or Drive trash (`TrashPath`), never for good. A kept original is in `ConvertResult.OriginalsKept` and the summary.
- Finishing a conversion after an update or Ctrl+R (6.1.0, Conner: "can it start after restarting if not finished"): `RunConvertAsync` registers `CarryOnTransfers.ForConvert` (Kind.Convert, note letter A: source and target pairs, format id plus `DeletesOriginals`, replaced sources as Clashed). The next start calls `FinishConvertAsync`: `AudioConverter.Remaining` lists Drive folders first (a folder that will not list throws, never read as empty), a target there and not being replaced is done, a source gone was done and deleted, the rest runs again. Never rename a converted file onto its deleted original's name: after a restart it would look like an original still to convert. A plain Quit, a crash or a reboot is not resumed.
- One file a core (`AudioConverter.Parallel`), each on `ArchiveWorkers.RunLong` at below-normal priority (Conner, 6.1.0: "make sure it uses all cores"). A file already in the chosen format is left out by name (`NotAlready`) and counted in the summary, except FLAC to FLAC and WAV to WAV, which he asked to keep.
- The Converting window is `ProgressForm(detailed: true)`: `TransferProgress.Tally` (converted, in progress, waiting, failed) and `Detail` (a line a file with its stage from `ConvertFile(stage:)` and percent, then failures). The Working on box is not refreshed while it has focus.
- Opus is encoded in sections on every core (src\OpusFileEncoder.cs, Conner: "get this as fast as it'll go"): thirty second sections (`SectionPackets`), each on its own thread with its own encoder, warmed up on the half second before it (`RollPackets`) and with prediction off on the packet either side of a join (measured without: the 20 ms at a join was ten times further from the original). Our own Ogg page writer puts the packets in one stream; Concentus.OggFile's writer is no longer used. The encoder is libopus itself (`NativeOpus`, native\win-x64 and win-arm64\opus.dll, 1.6.1, built in Documents\code\TTCode\opus with a static runtime, BSD, licence in `--licence`), about three times the managed one a core (132 against 45 times real time); `ManagedOpus` (Concentus) is the fallback when it will not load, and the suite holds both to the same join tests. Complexity is 10 below 192 kbps and 5 from there up (`ComplexityFor`; measured on a real recording at 320: 111 against 164 times real time a core, and nobody hears it up there). Sections are rented from an ArrayPool. Measured live: a 4.8 GB, 66 hour FLAC on Drive to Opus 320 in about 5 min 30 s (some 720 times real time), 7.2 of 8 cores, nothing on disk; it is the processor that limits it, not the network (6 MB/s down, 5 up of a line that does far more). Memory while it runs is about 1.9 GB, of which 1 GB is the mount's own read cache; a heap dump (dotnet-dump, dumpheap -stat -min 500000, gcroot) showed the rest had been the player readying the track under the cursor (`AudioPlayer._pending`, up to its 1 GB cache), so a conversion calls `Program.CancelAudioPrepare` and no track is readied while one runs (`MainForm._converting`). Opus at 320 of a quiet recording is bigger than its FLAC (libopus spends the rate asked for on silence too): his 66 hours were 4.8 GB as FLAC and 9.6 GB as Opus 320.
- Opus qualities run to 510 kbps (`AudioFormats.MostOpusKbps`); one channel is capped at 300 in `OpusFileEncoder`.
- Decode with TrackDecoder, encode: WAV and Opus (Concentus OpusOggWriteStream) ourselves; MP3, AAC and FLAC through the MF sink writer, which picks the container from the extension. This is encoding, not the playback chain, so the no-MFT rule does not apply. FLAC falls back to our own encoder (fixed predictors, Rice) when Windows has none. Encoders are probed with MFTEnumEx.
- Output goes to `.converting-*` with the target's extension and is moved into place only when complete. Never over a source, never over another source in the batch; replacing an existing file only when the person chose Replace (asked once per batch, `ConflictForm` with `filesOnly`).
- `AudioDecoder`'s MFStartup count and call are one step under a lock: the converter opens decoders in parallel, and the old Interlocked count let a second decoder use MF before the first had started it (0xC00D3E85).
- Windows reads no tags from WAV and refuses to write them; the summary says so. Opus tags go in OpusTags, FLAC (ours) in VORBIS_COMMENT, the rest through the property store after writing.
- The editor never writes until save. Its `EditList` is immutable (undo keeps the old one); `EditedDecoder` plays and renders it, through `WasapiPlayback.DecoderFactory`. Save writes "name (edited).ext"; Ctrl+Shift+S replaces the original only after a question, original to the Recycle Bin first.

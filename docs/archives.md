# Compressing and extracting

Part of the Explorer Native notes for Claude; CLAUDE.md says when to read this file.

## Compressing and extracting

- Context-menu commands only. `ArchiveFormats.All` is the format list. We do zip, tar and gzip ourselves; Windows tar does xz, bz2, zst, plus read-only formats; 7z goes through 7-Zip.
- 7z (4.2.1, Conner: much faster, all CPU and RAM but leave enough): 7-Zip Extra 25.01 `7za.exe` (native\win-x64 and native\win-arm64, LGPL, licence in `--licence`) is an embedded resource, unpacked to `%LOCALAPPDATA%\ExplorerNative-Zip\<ver>-<arch>` and checked by SHA-256 (src\BsdTar.SevenZip.cs, a partial of BsdTar). Windows tar ignores `7zip:threads` (measured: 490MB, 180s at 1 or 8 threads; 7-Zip 43s, extract 15s vs 5s). Runs with every core (`SevenZipThreads`; making 7z/xz at Balanced or Smallest asks two a core, `SevenZipMakeThreads`, because LZMA2 pairs an encoder with a match finder: -mmt8 used 4.2 of 8 cores, -mmt16 7.4, 1.6GB 257s to 148s), `-mmemuse=<free less headroom>m` (`SevenZipMemory`), below-normal priority, inside the tar job, the same CPU-time stall rule. Create takes a UTF-8 list file (`@list`, which must not follow `--`); locked files come from its "WARNINGS for files" and "Scan WARNINGS for files and folders" summaries. Extract goes into the same `.extracting-*` staging and `Rehome` as tar, `-aos` keeps the first of a repeated name, a dummy `-p` makes a protected archive fail instead of prompting. `UsesSevenZip` decides; `SevenZipOff` puts tar back for the crash test. tar.xz and tar.bz2 also go through 7-Zip both ways (`UsesSevenZip`, `UnpacksWithSevenZip`): two processes, a `Feeder` (tar to stdout when making, decompress to stdout when unpacking; progress and warnings on stderr, -bsp2/-bse2) piped into the second. Measured on 490MB: bz2 make 44s to 7.7s, xz unpack 11.3s to 3.6s, bz2 unpack 21s to 10s; xz make about even but 12 percent smaller. tar.zst stays with Windows tar (7-Zip cannot write it; tar is under a second). Timing tool: `EXPLORERNATIVE_SELFTEST_ONLY=archivebench` with `EXPLORERNATIVE_BENCH_DIR` (and `_BENCH_FORMATS`). Tests: `EXPLORERNATIVE_SELFTEST_ONLY=sevenzip` (seconds). `ArchiveEngine.RecommendedThreads` is every core too.
- System32 tar (libarchive 3.8.8) crashes on non-ASCII names. `BsdTar.Executable` falls back to a WinSxS copy and caches the choice. A fresh install may have no older copy (this dev VPS): tests gate on `BsdTar.HandlesNames`, and the crash is reported in words. Every tar starts through `StartQuietly` (SEM_NOGPFAULTERRORBOX, inherited at creation) and its job has DIE_ON_UNHANDLED_EXCEPTION: without them the crash put up "tar.exe - Application Error" and the operation hung behind it until OK (4.1.7, `CrashShowsNoBoxTests`; run archive tests alone with `EXPLORERNATIVE_SELFTEST_ONLY=archives`). A browse whose tar stopped part way is shown with `Partial` and never cached as whole.
- Only a source file that cannot be read is skipped; any failed write to the archive aborts it, so a Replace never puts a partial archive over a good one.
- libarchive loses non-ASCII names through text, so names go only as arguments or straight to disk. Never list bsdtar formats by name.
- Pass the format explicitly (`FormatFlags`), extract with `-k`, use junctions for long paths, judge stalls by CPU time. Stage into `.extracting-*` in the destination.
- Parallel deflate. One worker and sixteen must give byte-identical output.
- 4.2.5 (Conner: "use 100 percent of what's available but don't freeze the PC"): `ArchiveWorkers` owns how hard. Every core, every archive thread below normal priority (`Run` for short pool work, `RunLong` for anything that waits: writers, emitters, the job itself; blocking pool threads starved the gzip pieces and held tar.gz unpacking to one core), 7-Zip and Windows' tar in the below-normal class. Memory from what is free now less `Headroom` (2GB or 15 percent): `ZipBudget`, `SevenZipMegabytes`. The zip writer's lane goes back when a worker finishes, not when the entry is written; small stored files are read by workers; zip extraction hands out runs of 8MB or more biggest first (`BigFirst`). `ParallelGZip.Reader` cuts a .gz at every plain member header and inflates the pieces on every core, believing a piece only when it is exactly one member (trailer CRC and length); anything else is read the ordinary way from that piece on, so output and errors match GZipStream. Big tar entries go to a writer through a `Pipe` while the reader goes on. Extracted files of 1MB or more are preallocated (`PreallocateFrom`), falling back to a plain open. On x64 the CRC is PCLMULQDQ folding (`Crc32.Folded`, 13GB/s against 1.2GB/s for the tables, Release). Bench in Release (`-c Release`): Debug builds run the JIT unoptimised and every number is wrong. Tests: `ArchiveSpeedTests` (in the archives group).
- `SafeTarget` checks containment (UNC before trimming slashes). Folders are plan entries. Zip64 only when needed. UTF-8 flag on. CRC-32 is the ARM `Crc32` instruction, not `Crc32C`.
- Progress counts while compressing. Test progress with one file. Unreadable files are skipped, not fatal. Every archive written is round-tripped through bsdtar.
- Browsing (Enter on an archive): `Pane.Archive` is set and `CurrentPath` is a virtual path through the archive (`C:\x\a.zip\Disc 1`). Never probe, watch or read it as a folder; every command that writes refuses with `RefuseInArchive`, and its menu items are in `_archiveHidden`. Zip and tar are listed from their headers and one member is extracted on its own (`ExtractionRules.Selecting`, so SafeTarget still applies). bsdtar formats are extracted whole into `tree-*` in the cache, because their names are only right on disk. Not on the Drive letter, and not .iso (Windows mounts those).

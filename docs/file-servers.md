## File servers: SMB, FTP, SFTP (7.0.0)

Conner: "can you add samba or something to this? you choose the port, the drive or folder to host, and set things? its a setting tab. called smb server. add other types too... make it work on the google drive thing too", then "no webdav. its old and going away anyways". Never add WebDAV.

- Three Preferences pages, one shape (`SettingsForm.BuildServerTab(kind)`): SMB server, FTP server, SFTP server. Settings are plain scalars per kind (`SmbServerEnabled`, `...Folder`, `...Port`, `...User`, `...Password`, `...ReadOnly`, `SmbServerShare`), all off by default, ports 4450 / 2121 / 2222 (`FileServers.Default*Port`). `SftpServerHostKey` and `FtpServerCertificate` are `ThisPcOnly` and made by `FileServers.EnsureKeys` the first time that server is on. A reset turns the servers off.
- `FileServers` (src\FileServers.cs, owned by the tray) decides what runs: `Apply(settings, announce)` queues a reconcile on a worker; any change to a server's `Config` is a restart; `WhyNot` is the one rule set (folder, whole path, port, user, password of `ShortestPassword` 8, share name, two servers on one port), asked by Preferences before OK and again before starting. A folder that is not there (the Drive letter at start-up) is waited for: looked for every `LookAgainEvery` (15 s), silent at start-up for `SayWaitingAfter` (2 min), then said once. Never `Directory.Exists` for it on the UI thread. Messages are `server.started`, `server.stopped`, `server.failed`. Commands: smb-server-on/off, ftp-server-on/off, sftp-server-on/off (`SetFileServer`).
- The servers open files through the ordinary file system on worker threads, so the Drive letter is a folder like any other (it is answered by this same process: never from the UI thread). Windows' own SMB sharing was not an option: port 445 only, an administrator per share, and it will not share a WinFsp network volume.
- SMB is `SmbFileServer` over SMBLibrary 1.5.8.1 and SMBLibrary.Win32 1.5.8 (pinned exactly). Two reaches into the library, each with a test that fails if an update removes it: `SMBServer`'s private `Start(address, transport, port, smb1, smb2, smb3, timeout)` (the public ones only do 445 and 139), and `NTDirectoryFileSystem`'s private `CreateFile(nativePath, ...)` for `DriveRootStore`: the library builds paths as folder + "\" + rest, and a drive's folder already ends in "\" ("G:\"), so every open on a shared drive failed with STATUS_OBJECT_NAME_INVALID. SMB 1 is never offered. Sign-in is the library's own NTLM with its lockout (10 tries in 10 minutes). Read only is the share's `AccessRequested`. Verified live with Windows' own client: `net use \\127.0.0.1\share /user:name pw /TCPPORT:4450` (Windows 11 24H2 and later take a port), list, read, write, rename, delete, wrong password, read only, and G:\ listed.
- FTP (`FtpServer`) and SFTP (`SftpServer`) are our own, on the BCL only, sharing `ServedFolder` (src\ServedFolder.cs): `Resolve` is the one way a client's path becomes a path on this PC (no "..", no colon, no device names, no trailing dot or space, containment checked again after GetFullPath, links that leave the folder not followed), plus the failed sign-in throttle. FTP is passive only (PASV, EPSV), with explicit TLS (AUTH TLS, PROT P) when it has a certificate; uploads go to a temporary name and are moved into place. SFTP is SSH-2 with ecdh-sha2-nistp256, an ecdsa-sha2-nistp256 host key, AES-CTR and HMAC-SHA2, password sign-in only, and only the sftp subsystem (no shell, exec or forwarding), SFTP version 3. Verified live in the installed app: curl for FTP plain and with --ssl-reqd, Windows' own sftp.exe for SFTP (with -b it needs -o BatchMode=no or it never offers a password; the password comes from SSH_ASKPASS with SSH_ASKPASS_REQUIRE=force), each also reading a file off G:.
- The firewall button adds one rule for the executable (`FileServers.AllowThroughFirewall`, one elevated cmd running netsh by full path), so FTP's passive data ports are covered.
- Tests: `EXPLORERNATIVE_SELFTEST_ONLY=release700` (rules, SMB over a real socket with the library's own client on a free port, a whole drive through subst, the manager) and `fileservers` (FTP and SFTP, FileServerTests). The test project references the SMB packages too.

## 7.0.1: the servers' security review (Conner: "make sure none of the servers have bugs or security holes. this is very important. make sure every feature has commands")

Two independent read-only reviews (FTP with ServedFolder; SFTP) each ran their own attack clients against the real source, plus an audit of SMB. Neither found a way in without the password, out of the shared folder, or past read only. What they did find, each pinned in `tests\Release701Tests.cs` (group release701) or Release700Tests:
- Anyone who could reach the port could tie FTP or SFTP up without a password. Rules now, for any server written here: a connection is counted in the accept loop BEFORE a thread is made for it, and uncounted as the last thing its thread does; one address holds at most `MaxPerAddress` (16) places, this PC's own address excepted (Tailscale arrives from 127.0.0.1); everything before sign-in has ONE deadline (`SignInWithinMs`, `BeforeSignInMs`, a minute) enforced where bytes are read, never a timeout per read; the goodbye read (`HangUpGently`) is two seconds in all; SFTP refuses a second key exchange before sign-in.
- `SignInThrottle`: a locked-out address's note is never evicted (cycling through 2,048 addresses wiped lockouts), and `Braking` (30 wrong sign-ins a minute from anywhere) makes every password answer wait `BrakeDelay`, right or wrong alike: call `Throttle.Slow()` before answering any password.
- SMB went through the library's own store, which follows junctions: `SmbFileServer.ShareStore` now sits in front of every share, puts each open and rename through `ServedFolder.Resolve` (a file's own stream name, "a.txt:Zone.Identifier", is allowed: Explorer writes one on every downloaded file), never opens a link as a link, and answers NOT_SUPPORTED to every control code (FSCTL_SET_REPARSE_POINT makes a link), to setting security and to hard links. Anonymous, Guest and an empty password are tested refused.
- FTP uploads: delete the temporary file unless the upload finished (a dropped control connection used to throw past the cleanup); REST opens with FileMode.Open; no file is made before a transfer port exists; the data connection is disposed in a finally. `ServedFolder.List` opens the folder when called, not on the first row.
- The firewall rule is one elevated netsh run directly (`RunNetsh`), never through cmd; `FirewallAllows` asks unelevated whether it is there; the button reads Allow or Remove (`RemoveFromFirewall`).
- Over Tailscale by default (Conner: "it should work on tailscale by default on its own"): `TailscaleForward` runs `tailscale serve --bg --tcp <port> tcp://127.0.0.1:<port>` for each port of a server that starts, and `serve --tcp=<port> off` when it is turned off or moves, only ever touching a forward that points at 127.0.0.1 on the same port (the web app's 443 and anything of the person's is left alone). No admin, no firewall, never Funnel. Forwards are left in place at Quit (a forward to a closed port just refuses) and are idempotent at the next start. FTP therefore has fixed transfer ports, the eight after its own (`FileServers.FtpPassivePorts`, `PortsOf`), and `WhyNot` keeps other servers off them. Through the forward every client arrives from 127.0.0.1, so the per-address sign-in limit is shared by everyone on the tailnet. PASV still reports 127.0.0.1 there; clients use EPSV or ignore an unroutable PASV address. `FileServers.UseTailscale` is off unless the tray sets it, so the suite never runs the real tailscale.
- FTP `Encrypted connections only` (`FtpServerEncryptedOnly`, `requireTls`): USER and PASS answer 530 outside TLS, PROT C is refused, a transfer needs PROT P.
- Commands: `SettingCommands` gives every plain setting a command by its own name (`settings`, `setting <name> [value]`), found by reflection so a new setting needs nothing; secrets (`IsSecret`) only ever answer set or not set; the servers' own keys are not offered. A command answers in its own words by throwing `Commands.Answer`. Server commands: `<kind>-server-on/off/status`, `<kind>-server` (opens its page), sftp-server-fingerprint, firewall-status, allow-through-firewall, remove-from-firewall.
- Server pages hide everything but the first paragraph and the Turn on box while unticked, as the Audio page does.
- Known and accepted: SMB data is not encrypted (the library signs, it does not encrypt), and its lockout is per user name, the library's own; SFTP writes straight to the target, so a cut upload leaves a partial file; neither FTP nor SFTP starts a rekey itself.
